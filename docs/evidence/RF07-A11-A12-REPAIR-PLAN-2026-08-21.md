Status: **bounded repair candidate implemented; live post-fix verification still required**.

## Frozen checks

A11: say `number four`; the proposed value/label must be exposed, remain uncommitted, and focus must reach a useful confirmation/rejection action.

A12: say `not four`; it must not propose or record 4. Then say `number four`, reject it, repeat, and confirm. Rejection must preserve the stored answer; confirmation must record only the displayed proposal.

The frozen fixed data defines `number four`/`not four` for the **SUS five-point route**, where 4 is a valid response. A previous R3 observation was made after the audit had moved into NASA-TLX and produced a `Closer to Low, value 25, for Frustration` proposal. That observation remains valid historical evidence of the executed route, but the RF-07 retest must use the frozen SUS 1–5 context so the command and scale are semantically aligned.

## Evidence boundary

The page receives browser-provided text hypotheses. It cannot reconstruct a negation that the upstream recogniser omitted from every returned transcript. Therefore RF-07 must not claim that Web Speech can always distinguish `not four` from `number four`.

The safety boundary is instead:

1. one-shot final-result recognition;
2. multiple ranked alternatives when available;
3. bounded exact parsing rather than unrestricted fuzzy matching;
4. veto of unresolved negation/exclusion meaning in any returned alternative;
5. visible/hearable transcript + proposed answer;
6. no commit until explicit confirmation;
7. rejection and visible/native answer fallback remain available;
8. contextual hints are optional and must not be treated as a grammar or guarantee.

## Primary standards/platform basis reviewed

### Web Speech API / MDN / Chromium

- The Web Speech API returns one or more recognition hypotheses; `maxAlternatives` controls the maximum alternatives returned.
- `SpeechRecognition.phrases` / `SpeechRecognitionPhrase` provide **contextual biasing**, not a constrained grammar. They make supplied phrases more likely to be recognised.
- `SpeechRecognitionPhrase` and contextual biasing remain experimental/limited-availability features; `phrases-not-supported` is a defined failure mode.
- The Web Speech specification states that legacy grammars have been removed and no longer affect recognition, so adding JSGF grammar code is not a valid repair.
- The specification exposes a `confidence` estimate but does not provide a universal application threshold that would make an incorrect valid transcript safe. RF-07 therefore does not invent one.
- Contextual bias is treated as an optional enhancement, not the safety boundary.

### WCAG 2.2 error prevention

WCAG 2.2 SC 3.3.4 explicitly includes submission of test responses and requires a reversible, checked or confirmed mechanism. W3C technique G168 describes confirmation/cancellation of a selected action; G98 describes review/correction before final submission. The AQP proposal-before-commit design is aligned with that error-prevention principle, while the full review screen remains the final submission safeguard.

### Mature open-source comparison

`JamesBrill/react-speech-recognition` documents the Web Speech browser-dependence, recommends graceful fallback/polyfills for consistency, and keeps fuzzy command matching **off by default**; its documentation warns that fuzzy/interim matching can create false positives. RF-07 therefore keeps strict bounded parsing rather than adding Levenshtein/fuzzy command matching.

Searches of current GitHub, Web Platform Tests, the Web Speech repository and MDN implementations found `SpeechRecognitionPhrase` chiefly in specifications, platform tests, browser-facing examples and relatively new application demos rather than a mature cross-browser pattern that could guarantee negation recognition. No application-side mechanism can recover a negation that the upstream recogniser omitted from all hypotheses.

## Current implementation already retained before RF-07

The current branch already has several necessary safeguards from the earlier rc.4 hardening:

- `maxAlternatives = 5`;
- cross-alternative unsafe-negation veto;
- exact/declared-label parsing before general negation rejection, so a legitimate option beginning with `Not ...` is not disabled;
- no arbitrary number mining from surrounding prose;
- visible `I heard` transcript and proposed answer;
- explicit confirmation before commit;
- `phrases-not-supported` retry without experimental hints;
- visible answer buttons remain usable.

RF-07 therefore must be a **narrow improvement**, not a rewrite of the speech subsystem.

## Candidate selection after regression and call-site review

Two broader ideas were considered and rejected:

1. **Removing the existing wrapper hints** (`option`, `rating`, `value`, `answer`, `choice`). There is no standards or empirical basis here to claim that those previously tested hints are harmful, and the repository already has regression coverage for them. The first exploratory candidate removed them; CI correctly exposed the behavioural change through the existing contextual-hint test. That candidate was discarded rather than weakening the established test contract.
2. **Restricting hints to the five smiley values.** The same builder also supports the full 21-value NASA-TLX route, so filtering intermediate valid values would weaken another supported route.

A further call-site review found a real implementation constraint: `configureVoiceHints()` applies `hints.slice(0, 120)` before constructing `SpeechRecognitionPhrase` objects. A naïve per-value expansion can therefore starve later NASA-TLX values on the 21-value scale even when the hint builder technically contains them.

The retained candidate is deliberately additive and preserves that full-scale route:

1. preserve the existing displayed-number, spoken-number, `number`, `option`, `rating`, `value`, `answer`, `choice`, official response-label, endpoint/alias and landmark hints;
2. add exactly one bounded negation-preservation hint per allowed numeric value: `not <spoken value>`;
3. build two ordered groups rather than deleting any prior hint: **priority hints** contain every value's displayed/spoken form, `number <value>`, `not <value>`, official labels, endpoints/aliases and landmark phrases; **fallback hints** contain convenience wrappers;
4. de-duplicate after concatenating priority hints before fallback hints, so the existing 120-phrase runtime cap keeps all 21 NASA-TLX values and their safety-critical forms ahead of lower-priority wrapper variants;
5. leave the strict parser, unsafe-negation vocabulary, cross-alternative veto, confirmation semantics, hard runtime cap and unsupported-phrases fallback unchanged;
6. add dedicated regressions proving that SUS includes both `number four` and `not four`, retains the existing hint surface, rejects `not/note/knot/naught/nought four`, still vetoes an apparently safe first alternative when a lower-ranked alternative contains unresolved negation, and keeps `100`, `one hundred`, `number one hundred`, `not one hundred` plus both NASA endpoints inside the first 120 hints.

The contextual hints may improve the chance that the recogniser preserves the intended phrase; they are not proof that a live recogniser will do so. The four historical RF-07 cells can change only after real R3/R4 retesting on the exact candidate runtime.

## Stop rules

Do not:

- add fuzzy matching to make a failing transcript look successful;
- map `not four`, `note four`, `knot four`, `naught four` or `nought four` to 4;
- auto-commit a recognised answer;
- use a confidence threshold as if it were engine-independent evidence;
- restore deprecated speech grammars;
- force cloud/on-device processing without an explicit product/privacy decision;
- claim recognition accuracy or accessibility benefit from unit tests.

If R3 or R4 still fails because the browser/OS recogniser supplies the wrong valid transcript, retain that F and document the upstream limitation rather than weakening the parser.
